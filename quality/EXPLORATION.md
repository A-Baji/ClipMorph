# Exploration Findings

> Generated by Quality Playbook v1.5.6 — Andrew Stellman
> Date: 2026-09-24 · Project: short-form-content-converter

## Domain and Stack

ClipMorph is a Python 3.11+ command-line application that validates, converts, and uploads gaming videos to four social platforms. It also exposes an optional FastAPI service and Svelte dashboard. The primary output is a vertical video artifact plus a resumable job manifest and per-platform upload results. Runtime dependencies include FFmpeg, Whisper/WhisperX, OpenCV, Google APIs, Tweepy, and optional FastAPI/Uvicorn.

## Architecture

- `clipmorph/__main__.py` is the CLI entry point and coordinates preflight, conversion, resumability, upload, and cleanup.
- `clipmorph/cli.py` parses flags and flattens YAML/JSON configuration into runtime values.
- `clipmorph/preflight.py` is the trust boundary for input, media, geometry, output, title, and credential checks.
- `clipmorph/job.py` persists source identity, artifacts, steps, status, warnings, and platform results using a temporary file replacement.
- `clipmorph/workflow.py` is the shared CLI/web execution path and persists observable step state.
- `clipmorph/conversion_pipeline/` performs transcription, subtitle generation, editing, and FFmpeg conversion.
- `clipmorph/upload_pipeline/` maps common content to platform-specific clients and runs uploads concurrently.
- `clipmorph/web.py`, `service.py`, and `batch.py` expose job, batch, cancellation, transcript, and artifact operations to the dashboard.
- `frontend/` builds the dashboard into `clipmorph/web_assets/`; it is not a second processing implementation.

The main data flow is input file -> source hash and manifest -> preflight -> conversion or direct artifact -> artifact metadata/policy -> parallel platform uploads -> manifest status and cleanup.

## Open Exploration Findings

1. `clipmorph/workflow.py:47-49` returns immediately when cancellation is observed after preflight, and `clipmorph/service.py` owns cancellation state. Verify that the manifest transitions to a terminal cancelled state rather than remaining `preflight` or `running` forever.
2. `clipmorph/workflow.py:68-76` records conversion completion before upload begins, but cancellation during upload is not checked and the upload step is only marked completed after all platform results return. Trace web cancellation through `CancellationToken` and confirm partial cancellation is represented in the manifest.
3. `clipmorph/__main__.py:139-143` returns after `--no-upload` with status `completed`, while `workflow.py:73-76` returns without setting a terminal status for the equivalent web path. Compare CLI and web lifecycle parity for no-upload jobs.
4. `clipmorph/job.py:115-136` marks a manifest `partial_failure` whenever any recorded platform result is false, including a single failed result before all enabled platforms have reported. Check whether retries and resumed uploads can distinguish pending from terminal partial failure.
5. `clipmorph/__main__.py:157-163` contains two consecutive empty-platform checks. The first marks the job `published` when all requested platforms are already complete, but the second is unreachable in that branch. Verify that an explicit empty `--upload-to` selection is treated consistently with the documented empty-means-all configuration behavior.
6. `clipmorph/cli.py:117-121` applies config values only when an argparse destination is absent. Because argparse creates destinations with defaults, verify that YAML values actually override parser defaults as documented, especially booleans and platform lists.
7. `clipmorph/preflight.py:109-121` checks only the credential names in `PLATFORM_CREDENTIALS`, while `clipmorph/auth.py:17-48` defines additional refresh/access/token fields. Verify whether a platform can pass preflight with only an identifier and then fail during client initialization.
8. `clipmorph/upload_pipeline/__init__.py:228-260` constructs platform results concurrently and maps initialization failures into results. Verify that result keys, policy blockers, exceptions, and manifest platform names are normalized identically across success and failure paths.
9. `clipmorph/policy.py:87-114` truncates captions in metadata but does not add a blocker. Trace whether platform clients consume transformed metadata or the original content, otherwise the policy decision can report an allowed artifact while the uploader sends over-limit text.
10. `clipmorph/job.py:73-90` loads JSON manifests without validating schema version, source fields, or platform/step shapes. Verify behavior for malformed, stale, or partially written manifests beyond the atomic writer's normal path.
11. `clipmorph/__main__.py:177-207` builds artifact metadata from FFprobe and then uploads, while `workflow.py:77-82` calls the uploader without equivalent artifact metadata or policy validation. This is a cross-entry-point parity risk for unsupported codecs, dimensions, and file size.
12. `clipmorph/preflight.py:40-43` uses `next(...)` for layout video selection after `_validate_video_stream`, but the layout branch reads `info["streams"]` directly. Verify malformed FFprobe responses do not produce an uncaught `StopIteration` in the web service.

## Quality Risks

1. High: because `execute_job` at `clipmorph/workflow.py:47-49` returns on cancellation without persisting a terminal status, a user cancelling after preflight may see a job that remains resumable as `preflight` or `running` instead of `cancelled`, causing queue and retry ambiguity.
2. High: because the shared workflow at `clipmorph/workflow.py:77-82` does not pass artifact metadata through `validate_artifact` before upload, an artifact rejected by the CLI path can reach web-triggered platform clients, producing inconsistent safety behavior across documented CLI/web parity.
3. Medium: because `JobManifest.record_platform` at `clipmorph/job.py:127-136` derives status from all currently recorded results, a retry of one platform can overwrite a previously meaningful partial state and make completion depend on the order in which concurrent results arrive.
4. Medium: because `_apply_config_defaults` at `clipmorph/cli.py:106-121` tests `hasattr` after argparse parsing, a config file value may be ignored whenever argparse initialized the destination with a default. This would make documented configuration precedence silently wrong while the command still succeeds.
5. Medium: because `validate_artifact` at `clipmorph/policy.py:104-110` stores a truncated caption only in `decision.metadata`, a caller that ignores that metadata can send the original over-limit caption. This is a domain-specific policy/enforcement split that produces plausible but invalid uploads.
6. Medium: because `PreflightValidator._validate_credentials` at `clipmorph/preflight.py:109-121` checks a reduced credential set compared with the platform clients and auth schema, a job can pass preflight and fail later during upload initialization rather than receiving a complete preflight warning.

## Skeletons and Dispatch

The job lifecycle states are represented by `status`, `steps`, and per-platform result dictionaries in `job.py`, `workflow.py`, and `__main__.py`. Platform dispatch is split between the enabled-platform map in `UploadPipeline` and platform modules under `upload_pipeline/platforms`. Configuration dispatch is split between CLI argument destinations and flattened config keys. The main completeness risks are lifecycle terminal states, parallel result aggregation, and duplicated CLI/web orchestration.

## Pattern Deep Dive - Fallback and Degradation Path Parity

The CLI path in `__main__.py:139-143` explicitly sets `completed` for `--no-upload`, while the shared web path in `workflow.py:73-76` returns immediately after setting the artifact and conversion step. The service layer therefore controls whether a web no-upload job is later finalized, and the parity contract in `docs/CLI_WEB_PARITY.md` says both paths create the same manifest and workflow. Review the caller in `service.py` and the API response state after this return; a missing terminal transition would be an absence bug.

## Pattern Deep Dive - Dispatcher Return-Value Correctness

`UploadPipeline.__init__` at `clipmorph/upload_pipeline/__init__.py:48-84` captures constructor exceptions into `initialization_errors`. Its `run` method then merges those errors with worker results at the return boundary around lines 228-260. `JobManifest.record_platform` at `job.py:127-136` immediately derives global status from the currently known platform values. Review whether the dispatcher returns one normalized result per requested platform and whether partial order-dependent recording can make a retry or concurrent completion look terminal too early.

## Pattern Deep Dive - Cross-Implementation Consistency

The CLI assembles FFprobe metadata at `__main__.py:177-207` before calling `UploadPipeline.run`, whereas `workflow.py:77-82` calls the same uploader with configuration but no equivalent metadata/policy decision. The preflight validator is shared at `workflow.py:28-43`, but artifact capability rules live separately in `policy.py:45-114`. A parity review should compare the exact effective configuration, metadata, policy blockers, and terminal status for CLI and web execution of the same manifest.

## Pattern Deep Dive - API Surface Consistency

`docs/CLI_WEB_PARITY.md` names resume, cancellation, cleanup, transcript review, batch submission, and upload retry as paired surfaces. The CLI invokes these concerns through `__main__.py`, while the web service routes delegate to `JobService` and `execute_job`. The critical check is not route existence but whether each route persists the same manifest fields and terminal states as the CLI. Trace `JobService.resume_job`, cancellation, and artifact deletion into `JobManifest.save` and compare their error responses with CLI exceptions.

## Candidate Bugs for Phase 2

1. Cancellation may leave shared workflow manifests non-terminal (`workflow.py:47-49`; open exploration and risk analysis). Review every cancellation return and assert a persisted cancelled status and resumability policy.
2. Web execution may bypass artifact capability policy (`workflow.py:77-82` versus `__main__.py:177-207`; pattern deep dive). Review whether unsupported artifacts can reach upload clients through the API.
3. CLI configuration precedence may ignore YAML values because argparse destinations already exist (`cli.py:106-121`; quality risk). Add focused tests for false/empty/list values overriding parser defaults.
4. Platform state may be order-dependent during concurrent upload and retry (`job.py:127-136`, `upload_pipeline/__init__.py:228-260`; dispatcher pattern). Verify pending, partial, success, and retry transitions with out-of-order results.
5. Policy truncation may not reach the actual uploader (`policy.py:104-110`, platform mapping in `upload_pipeline/__init__.py`; cross-implementation pattern). Verify the sent caption equals the transformed policy metadata.

## Derived Requirements

- REQ-001 [Tier 3]: Every cancellation path must persist an explicit terminal or resumable state and must not leave a job indefinitely active.
- REQ-002 [Tier 3]: CLI and web execution must apply equivalent preflight, capability policy, artifact metadata, and terminal-state rules.
- REQ-003 [Tier 3]: Configuration precedence must allow explicit CLI values to override config values, and config values to override parser defaults.
- REQ-004 [Tier 3]: Concurrent and retried platform results must preserve per-platform success/failure state without order-dependent global corruption.
- REQ-005 [Tier 3]: Any policy transformation, including caption truncation, must be the value consumed by the platform uploader.
- REQ-006 [Tier 3]: Resume must validate source identity and preserve artifact and platform state across process restarts.

## Derived Use Cases

- UC-01: A creator validates a job, cancels it, and sees an accurate resumable or terminal status.
- UC-02: A creator submits the same effective job through CLI or dashboard and receives equivalent validation and lifecycle results.
- UC-03: An operator configures defaults in YAML and overrides selected values at the command line.
- UC-04: A creator uploads to several platforms, handles partial failure, and retries only incomplete destinations.
- UC-05: A creator resumes a job only when the source file still matches the recorded identity.
